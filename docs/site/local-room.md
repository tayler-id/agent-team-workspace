# Local room

## What it is

One explicitly started, loopback-only development room with one fixed human principal. L1 defines its language-neutral contracts; L2 persists messages in PostgreSQL; L3 adds an owned runtime and cursor replay. L4's first slice serves the apps/web room shell over that runtime. This is **not the finished room UI**, production identity or a hosted deployment.

L1 published the conversation contracts, one JSON Schema 2020-12 family in [local-room.schema.json](repo:contracts/schemas/local-room.schema.json) with a closed command, message and event family. L2 makes the room durable: a send is committed to PostgreSQL in one transaction, and the room reads back in the same order after the service restarts. Cursors and the base receipt reuse the [synchronization values](repo:contracts/schemas/sync.schema.json); errors reuse the [stable reason codes](repo:contracts/schemas/errors.schema.json), which now include `command_conflict`.

L4 owns the usable room interface; L5 owns the bounded local response. L4's first vertical slice has landed: the apps/web room shell (App, Timeline, Composer) that the development fixture uses also runs against the live L1-L3 runtime over its own Host transport, replacing the old plain-DOM harness. [Live room UI](#live-room-ui) lists what it covers and the L4 work that remains. L5's pure preparation core remains independently testable. A first posted L5 slice now quotes one or more selected persisted messages through the same room event stream used by CLI and browser. It is a deterministic local fixture, not a model provider or a general question-answering agent; this slice does not complete all L5 qualification.

## What it does

Run these commands from the checkout root. No database URL or external account is needed:

```sh
node scripts/local-room.ts doctor
node scripts/local-room.ts start
node scripts/local-room.ts send --body 'Hello from the local room'
node scripts/local-room.ts history # copy a persisted message_id
node scripts/local-room.ts answer --selected-id UUID --command-id UUID # reuse the ID to retry
node scripts/local-room.ts history
node scripts/local-room.ts replay --after 0
node scripts/local-room.ts evidence
node scripts/local-room.ts stop
```

Open the `url` printed by start. It serves the same apps/web room shell (App, Timeline, Composer) used by the development fixture, now over `apps/web/src/host/live.ts`: a Host transport that sends through the same HTTP command as the CLI and displays the **client-core committed projection**, not an optimistic timeline. The page connects on load and polls committed events. The header's status region carries a **Disconnect** button once a room is loaded; while disconnected it becomes **Reconnect**. Disconnect cancels the in-flight poll and any in-flight command retry (their fetch is aborted) without touching client-core's committed state; Reconnect resumes polling from the room's own applied cursor and resends every command left waiting on `wait_connection`, each by its own exact identity. A message typed and sent while still Disconnected waits for Reconnect the same way an offline send does, rather than attempting on the controller Disconnect already aborted, which would otherwise read back as a permanent denial instead of a connection wait. Browser `online`/`offline` events (not a fabricated heartbeat) distinguish `offline` from `retrying`: a poll failure while `navigator.onLine` is true reads `Retrying the connection.`; while it is false it reads `Offline: sends wait for a connection.`. While the service is down the status reads `Connection error`, and polling resumes from the last applied cursor when it returns, including after `stop` and `start`. A send that fails because the server is unreachable, timed out, answered 408 or 5xx, or rate-limited retries its frozen command with the same ID. Pressing Send again on the same unchanged draft while that command is unsettled reuses it, so the room gets one message. Any other rejection stops at once. A 4097-character body, for example, gets one 400 `malformed_command`, which the command's own line in the composer shows as `Failed: HTTP 400 malformed_command.` with a **Discard, edit and send again** button; the draft itself is kept untouched (see [per-command delivery feedback](#per-command-delivery-feedback) below). The composer also caps typing at the 4096-character wire limit. An unsent draft survives reload: it is written to this tab's `sessionStorage` under a key scoped to the room's project and room IDs, restored once on the first snapshot after page load, and cleared when its send succeeds or the box is emptied by hand. See [unsent drafts](#unsent-drafts-across-reload) below.

```flow
Connecting | Initial load or the moment Reconnect is pressed, before the first poll settles.
Online | The last poll or send succeeded; navigator.onLine is true.
Retrying | A poll or send failed transiently while the browser still reports a network.
Offline | The browser's own online/offline event reports no network, observed, not pinged.
Disconnected | The user pressed Disconnect: polls and command retries are cancelled and stay cancelled until Reconnect.
```

Ordinary stop/start preserves the database and URL. Only `reset --confirm-disposable`, while stopped, removes that instance's disposable data. It is not an undo, backup or migration rollback. Use `--instance NAME` on every command for a separate development instance. Each instance has its own cluster, listeners and credentials, but the same fixed room IDs, not multi-room provisioning. [The CLI reference](cli.md#local-room-runtime) lists flags and structured results.

### Selected local quotations

A separate pure core can prepare an attributed quotation of explicitly selected stored messages. Its visible label is **Deterministic local fixture (not AI inference)**. Each claim is only that the cited record contains the quoted text, not that its contents are true. It neither answers arbitrary questions nor follows instructions inside messages. Embedded citations and links stay data and never expand the selection.

In the live room, **Quote locally** on a human message posts a response; once a committed local-agent quote arrives the source button reads **Quoted locally** and is disabled in that tab, including after reload. Before posting, the browser stores the action's command ID under its room and selected-message key. If the response is lost, retrying that action, including after reload, reuses the ID and returns the original receipt. A successful receipt clears the pending ID, so a later explicit action can use a new ID. The current timeline intentionally labels an already-quoted source **Quoted locally** and disables its button, including after reload; this is an explicit visible UI choice rather than a server-side ban. This is per-browser storage; a distinct tab that independently starts an action before observing the committed event can still create a distinct response. `answer --selected-id UUID` uses the same `POST /api/v1/local-room/answer` path and requires the caller to reuse `--command-id` to replay a lost receipt. For HTTP, `selected_ids` accepts 1-10 persisted message IDs and an explicit `command_id`. A missing ID, repeated selection or foreign scope is refused. Reusing an ID and the same selection returns the original receipt across restarts; reusing it for another selection conflicts. These are exact attributed quotations, not summaries, truth assessments or instructions. There is no Ask center free-text question interface.

#### Action retry, not selection dedupe

```flow
Explicit click | Generate and persist an action command ID before sending the selected IDs.
Lost response | Keep the ID; retry after reload with the exact same action payload.
Committed receipt | Validate matching command ID, then clear the pending action key.
Later explicit click | The cleared key causes a new ID and permits another intentional quote.
Separate tab | Independent actions can race before event polling; cross-tab action coordination remains unqualified.
```

## Why it exists

A receipt can be lost after PostgreSQL has committed. A client can disconnect between a snapshot and its next event. The room must still converge without duplicating a message or inventing a cursor. L2 commits the counter, immutable message, event and command receipt together under a room lock and forced project row-level security. Same actor, command ID and digest replays the original receipt; a changed body is 409 `command_conflict`.

L3 reads those committed event rows, never in-memory notifications. The snapshot's state and cursor come from one repeatable read. Reading strictly after that cursor covers messages committed while the snapshot was travelling. Client core deduplicates stream sequences, buffers gaps and refuses older revisions. A receipt settles a command but **never advances the room cursor**. This is why acceptance, delivery and reading remain distinct.

## How it works

```flow
Doctor and allocate | Check Node/PostgreSQL; exclusively claim the instance path. Refuse existing foreign or ambiguous paths and occupied listeners.
Launch and prove ownership | Start a private SCRAM-protected PostgreSQL child and center. A fresh 256-bit launch key authenticates a nonce bound to the launch, paths, listener and process inventory.
Snapshot at cursor C | Read state and counter together; show only the immutable client-core projection. Concurrent later commits are not lost.
Replay strictly after C | HTTP reads at most 50 committed events in numeric sequence order. Apply contiguous events, deduplicate copies, buffer gaps and repeat after the applied cursor.
Browser Host transport | apps/web's live transport feeds each snapshot and event page into client core. App, Timeline and Composer render only that committed projection. Send posts the same HTTP command as the CLI; the receipt settles the command and never inserts a row.
Disconnect and resume | The CLI adapter cancels bounded HTTP reads; the browser keeps polling. Both resume from the applied cursor, including across ordinary service stop/start. A transient failure retries the unsettled command with its original ID and bytes; a permanent rejection stops.
Selected response | The posting adapter locks the room and reads selected persisted records inside one project-scoped transaction. The pure compiler bounds and sorts the context, then the proposal supplies direct citations. Append the labelled local-agent response, event and dedupe receipt atomically; two browsers see the same committed row.
Stop or explicit reset | Authenticated stop shuts down the owned child, proves listeners absent and retains data. Separate confirmed reset checks stopped ownership and deletes only that disposable instance path.
```

### Live room UI

`scripts/local-room-service.ts` builds [`apps/web/src/main-live.tsx`](repo:apps/web/src/main-live.tsx) with the same standalone-Ajv aliasing it already applied to the plain harness, so the served bundle still needs no `unsafe-eval`. That entry mounts the same `App` shell described in [the web shell](local-room-web-shell.md) over [`createLiveTransport`](repo:apps/web/src/host/live.ts), which polls `GET events?after=CURSOR` on the same 250 ms cadence as the CLI adapter, posts `SendRoomMessageCommand` on submit, and feeds each failure to the client-core `retry` input. An unreachable server, a timeout, 408 or 5xx resends the same command; 429 waits for `Retry-After`; any other 4xx, a schema-invalid receipt or a receipt naming another command is `denied` and stops. The route passes `live` to `App`, which swaps fixture wording for local-room labels. Per-message author and the stored time come from the wire `RoomMessage.author`/`created_at`, rebuilt on every snapshot and event since L1 carries no display name; the timeline shows a locale-aware reading of that timestamp and keeps the wire value on the time element ([message times](local-room-time-display.md)); the header project/room/member chrome is a fixed placeholder, because L1 has no project or room naming concept yet. Real connection state (`connecting`/`online`/`retrying`/`offline`/`disconnected`, derived from the browser's `online`/`offline` events and observed fetch outcomes, never a synthetic heartbeat) and the manual Disconnect/Reconnect control that cancels in-flight polls and command retries are landed; see the state table above. Per-command delivery feedback (below) replaces the old aggregate pending count. Unsent drafts that survive reload are landed too; see [unsent drafts](#unsent-drafts-across-reload). Remaining L4 work, not in this slice: retained latency, bundle and replay measurements; and a VoiceOver pass. The header's project and room names stay fixed placeholders until a contract carries them.

#### Unsent drafts across reload

The composer's draft lives in client-core's in-memory state, same as before; the Host transport is the only thing that also mirrors it to the browser so a reload can restore it. `apps/web/src/host/live.ts` writes each change through `RoomTransport.saveDraft` to `sessionStorage` at `agora.local-room.draft:PROJECT_ID:ROOM_ID`, alongside the room's committed cursor at write time. This bounds the mechanism to the minimum a reload needs: `sessionStorage` scopes the value to this tab's session and clears it when the tab closes, so it never leaks to a new browser session or (since each disposable instance listens on its own port, hence its own origin) a different instance. A tab opened fresh (a new window, a typed URL, a bookmark) gets its own empty `sessionStorage` and never sees another tab's draft. **Limitation:** per the [WHATWG storage spec](https://html.spec.whatwg.org/multipage/webstorage.html#dom-sessionstorage-dev) and matching browser behavior, a *duplicated* tab or a session restored after a browser restart is handed a copy of its opener's `sessionStorage`, so a duplicated tab can briefly show the same unsent draft as the tab it was duplicated from; this is accepted as standard `sessionStorage` semantics and was not built around. A distinct tab that types its own text afterward diverges immediately, since each tab's `sessionStorage` writes are independent from that point on.

The disposable process's identity rides on the snapshot response itself: `scripts/local-room-service.ts` stamps an `x-agora-instance: LAUNCH_ID` header on every response it serves, and the live transport reads that header off the exact snapshot fetch it just applied, never from a second request. This was a header on a separate `GET /_runtime/identity` call in an earlier revision; a review found that a reset landing between that call and the snapshot fetch could attach the OLD instance to the NEW room's cursor-0 snapshot, so the two are now bound to one response by construction. No second request is left for a reset to race. `/_runtime/identity` still exists, unauthenticated, for the CLI's own ownership checks, but the browser client no longer calls it. Every draft write and every draft/pending read requires that header to be a nonempty string; restoring a saved draft or reusing a saved pending command needs the stored id to equal that verified current id by strict comparison. A disposable reset that had advanced the cursor before resetting is still caught by the cursor check alone; a reset of a room that was still at cursor `0` mints a fresh process (`local-room start` always generates a new launch id, reset or not) and so is caught by the id check even when the reused port keeps the cursor at that same `0`. **Limitation:** a snapshot fetch that fails, times out, or comes back with a missing or blank `x-agora-instance` header is never treated as "no check needed". It fails closed. A draft typed while the header is unavailable is not saved at all, and a draft saved earlier is not restored on a reload where the header is unavailable; the room is otherwise fully usable, only unsent-text persistence is sacrificed for that one write or read. This trades a small amount of reload convenience for the alternative, which is worse: showing one disposable instance's leftover text under a different one.

The saved text is capped at the composer's 4096-character wire limit. A successful send only clears the saved entry when the composer still holds the text that send settled, so typing a new, still-unsent message while an earlier send is in flight survives that earlier send's receipt; emptying the composer by hand also clears the saved entry; a failed or still-retrying send leaves it in place. `submit()` separately mirrors a still-unsettled send's `command_id`/`request_digest` to `sessionStorage` at `agora.local-room.pending:PROJECT_ID:ROOM_ID` (same verified-instance stamp, same fail-closed rule) before the POST resolves, so a reload while that POST's outcome is still uncertain does not lose the identity: pressing Send again on the same unchanged text reuses the saved `command_id` instead of minting one the server has never seen, and the server's own actor/command_id idempotency replays the original receipt instead of committing a second message. That record clears once the command settles or is permanently denied. The engineering fixture transport implements `saveDraft` as a no-op, since it never reloads a real page. `apps/web/test/live.test.ts` covers reload restore, a failed send keeping the draft, a successful send clearing it, typing over an in-flight send without losing the new text, a deliberate clear, the reset-to-a-lower-cursor discard, a reset still at cursor 0 told apart from an ordinary reload by process identity, a still-unsettled send reusing its command id across a reload instead of duplicating, a snapshot with no verified identity at save time never persisting the draft, a reload snapshot with no verified identity failing closed on a draft saved under a verified instance, a malformed/empty identity header treated the same as an outage, a pending command id not reused once a reload's snapshot carries no verified instance, and (regressing the header-binding fix itself) that no separate `/_runtime/identity` request is made at all.

```flow
Type in the composer | onChange applies `draft` to client-core state and calls Host `saveDraft`, which writes `{cursor, text, instance}` to this tab's sessionStorage under the room's project/room key only if the current instance was just verified nonempty; otherwise it clears any stored entry instead of writing one.
Reload this tab | The live transport's first snapshot fetch after page load reads its own `x-agora-instance` response header, then that draft entry once; it is restored only if the current instance is a verified nonempty id, that id strictly equals the stored one, and the stored cursor is at or before the room's current cursor.
Press Send | `submit()` first checks for a saved pending command_id for this exact still-unsent text under the same verified-instance rule and reuses it if present; otherwise it writes the caller's fresh command_id/request_digest to sessionStorage before the POST resolves.
Send succeeds | The receipt settles the command; only if the composer still holds the exact text that was sent do client-core and the sessionStorage draft entry clear, so text typed afterward is left alone. The pending-send entry always clears on settlement.
Send fails or is still retrying | The draft and its sessionStorage entry are both left untouched, so a later reload sees the same unsent text; the pending-send entry also survives so a resend reuses the same command_id.
Empty the box by hand | An empty `saveDraft` call removes the sessionStorage draft entry immediately, the same as a successful send.
Disposable reset | The restarted process's fresh identity fails the instance check even if the cursor is unchanged, so a stale draft (and any pending-send record) from before the reset is discarded instead of resurfacing. Bound to the one snapshot response, so no separate request can race the reset.
Snapshot identity missing, blank, or the fetch itself fails | Fails closed on both sides: nothing is saved while it is unavailable, and nothing already saved is restored or reused until a verified matching id is available again.
```


### Per-command delivery feedback

The composer used to show only "N pending commands awaiting a receipt," which never changed once a send was permanently rejected: the failed command stayed counted as pending forever, with no way to see why it failed or to dismiss it. Each send now gets its own line naming its real state, sourced from two owners that never overlap: the transport (`apps/web/src/host/live.ts` and `apps/web/src/host/fixture.ts`) reports `sending`, `retrying` or `waiting_connection` while a command is still in flight; `@agora/client-core` reports `delivered` or `failed` once it has settled the command for good. A failed line carries the server's own reason text (for example `HTTP 400 malformed_command`) and a **Discard, edit and send again** button, so the failure is legible without color and there is an explicit way to clear it.

```flow
Sending | Enter/Send just posted the command; no attempt has failed yet.
Retrying | A prior attempt at this exact command was transient (unreachable, timeout, 408, 5xx or 429); the same command ID retries.
Waiting for a connection | The browser is offline or the room is Disconnected; the command holds until Reconnect or the network returns, still with its original ID. Two or more commands can wait at once, each by its own identity: client-core tracks an offline submit as a real pending command instead of only the transport remembering it, so a second offline send never overwrites or drops the first.
Delivered | client-core marked the command's tag `received`: the server accepted it and the message will appear once its event applies.
Failed | client-core marked the command's tag `denied` with the failure's reason: any 4xx other than a timeout, a schema-invalid receipt, or a receipt naming another command. This is terminal; Discard removes the record.
```

`denied` is a permanent outcome, never a transient one: client-core marks the command `denied` once, the transport stops retrying it, and neither side revisits it. `discard` (a new `ClientInput`) only removes a command already tagged `denied` from `state.commands`; it is a no-op on a still-pending or already-delivered command, so it can never cancel an in-flight send or erase a real receipt. Discarding never touches the draft text and never itself sends anything, so a permanent rejection can neither quietly retry itself nor be discarded into a duplicate: the next send is always a deliberately new command ID, exactly like editing the draft and pressing Send today. [`packages/client-core/test/sync.test.ts`](repo:packages/client-core/test/sync.test.ts) proves the denial/discard/resend identity chain against the pure core; [`apps/web/test/live.test.ts`](repo:apps/web/test/live.test.ts) proves the same real 400 `malformed_command` response reaches this state over the live HTTP transport, alongside the existing sending/retrying phase transitions; [`apps/web/test/app.test.tsx`](repo:apps/web/test/app.test.tsx) drives Discard through the rendered composer.

#### What happens when a send is lost, delayed or rejected

**What**: every send you make keeps one identity (its command ID) from the moment you press Send until it is either delivered or permanently failed. If the network drops a response, if the server is briefly overloaded, or if the room disconnects, the composer keeps retrying that exact same command instead of starting a new one. Only a genuine rejection (a body that is too long, for example) stops the retries and asks you to act.

**Why**: without a stable identity, a retry after a lost response could look like a second message to the server. The room already recognizes a repeated `(command_id, request_digest)` pair as the same request and answers with the original receipt instead of creating a duplicate, so retrying is always safe.

**How**: `apps/web/src/host/live.ts` classifies each failed attempt (unreachable, timeout, `408`, `5xx`, `429`, or a genuine `4xx`) and either resends the frozen command or marks it permanently failed; `@agora/client-core` is the single source of truth for which commands are still pending, delivered or failed, so the composer's status lines and the Discard button always agree with what actually happened.

```flow
Sent | You press Send; the command gets one ID that never changes for this attempt.
Retried | The first response never arrived, or the server was briefly unreachable or overloaded (`408`, `5xx` or `429`); the same ID is resent, proven against a mocked server in apps/web/test/live.test.ts.
Recognized | If the earlier attempt had actually committed, the room recognizes the identical ID and digest and returns the original receipt rather than creating a second message.
Delivered | The command settles once, and exactly one message appears in the room.
Rejected | A genuine problem (an oversized body, for example) stops retries at once and commits nothing; Discard clears the failed line without touching your draft or resending anything.
```

[`evidence/local-room/delivery-feedback/receipt-failure-browser/README.md`](repo:evidence/local-room/delivery-feedback/receipt-failure-browser/README.md) drives the real served room: a lost receipt (the request truly commits server-side, only its response is dropped) and a simulated transient failure each retry the same command ID against the real server and commit exactly once; the room's own rate limiter is separately shown to return genuine `429`s under real concurrent load; the permanent rejection commits nothing and leaves the draft for Discard.

#### Unread, announcements and touch targets

The header shows `N unread` and a **Mark room as read** button. A message you send never counts as unread. Once client core has applied the event named by your own send receipt, it moves the room's last-seen sequence up to that message, whichever of the two arrives first. Anything older that was still unread is marked read with it, because unread is one last-seen sequence per room. Matrix moves its read marker the same way when you post.

The status region is a polite live region. When unread grows, it waits 2 seconds so a burst reads as one notice, then says `1 new message, 2 unread.`, the same total as the header. Loading the room, reloading, and your own sends announce nothing. Marking the room read, or the next arrival, clears the old notice at once, so it never shows a total the header disagrees with. Arrow keys, Page Up, Page Down, Home and End move focus between messages. Only one message sits in the Tab order.

The first unread message also carries its own boundary marker, matching [`Screen-Room`](repo:docs/design-handoff/results/design-system/components/Screen-Room/README.md)'s "live chip and a faint rule": a pill reading `N new` with a small live dot, followed by a hairline that runs to the row's edge. It is a `role="separator"` naming the same count out loud (`aria-label="Unread messages start here, N new"`), so a screen reader gets the count without waiting for the debounced status announcement above. It moves with the real unread cursor: it appears on the message where `firstUnread` first turns true, and disappears the moment **Mark room as read** (or the next read) advances the cursor past it, exactly like the boundary it replaces. The dot's pulse is muted like every other animation under `prefers-reduced-motion: reduce`.

```flow
You send | The receipt settles your command. Client core remembers the committed sequence it names but does not move the cursor.
Your event arrives | Polling applies the event. Its sequence is now at or below the cursor, so last-seen rises to it. Header stays `0 unread`, no New boundary, no announcement.
Someone else posts | The CLI, another tab or the local agent commits a message. Unread grows by one and the header updates at once; any old notice clears.
Two seconds later | The status region says `1 new message, 1 unread.` A screen reader reads it once.
Mark room as read | Last-seen moves to the cursor. Header reads `0 unread` and the notice clears.
```

In the phone shell (700 px wide or less) and under any coarse pointer, every button is at least 44 by 44 CSS px. Wider approved controls keep their width, so Send stays 88 px wide. With a mouse or trackpad on a wider window, buttons keep the approved 40 px height. Read state lives in the page session only: a second tab still counts the first tab's messages as unread, and a reload starts at `0 unread`. [Finding verdicts and receipts](repo:evidence/local-room/usability-fixes/README.md) record which review findings reproduced and which did not.

The approved direction for the room's presentation is [the design results](repo:docs/design-handoff/results/README.md): `tokens.json`, the brand and component READMEs, `state-matrix.md` and the desktop and phone frames. Since `1d9584d` the served page uses its light tokens, Cal Sans UI and Cal Sans Text, rounded controls and pill buttons, and narrow-screen spacing; [the web shell](local-room-web-shell.md) describes that adaptation. Measured against the full baseline, the page still differs in these ways:

- **Fonts in the served room.** The local runtime's content security policy has no `font-src`, so it blocks the inlined Cal Sans files and the page falls back to `system-ui`. IBM Plex Mono for data is not wired.
- **Shell.** The page is one column: header, status, timeline, composer. `Screen-Room` puts rail, timeline and pane in one white frame. There is no rail, no pane and no phone nav.
- **Header.** The crumb is now two-tone (project grey, room ink) and the project agent's `not_enabled` state is its own explicit chip beside the lifecycle chip, matching `RoomHeader`; see [header alignment](repo:evidence/local-room/header-alignment/README.md). `RoomHeader` still wants repository and search, which this single-person local-only prototype does not have and does not claim.
- **Chips and alerts.** The lifecycle chip is a filled pill without the baseline's small state dot. The alert still uses a thick left border, and `OfflineBanner` in the state matrix replaces it.
- **Composer.** `Composer` wants a toolbar of present agents, Ask center and Create task as soft pills, and named over-limit, offline, rate-limited and observer states. The page has a textarea, a Send button and one text line per command naming its own delivery state.
- **Timeline.** The unread boundary is now the baseline's live chip and faint rule, see [unread boundary](repo:evidence/local-room/unread-boundary/README.md). The baseline's tiles for typed work objects are not implemented; messages still render as plain text and code blocks.

The room UI is not complete until these land.

The narrow development transport is bounded HTTP polling using the existing Hono HTTP surface: `GET /api/v1/local-room/events?after=CURSOR`. Each page is a schema-validated `RoomEventBatch`; an empty page means caught up. Polling uses 250 ms between attempts, a five-second read timeout and cancellation. This does not claim the production R07 WebSocket handshake, subscription or queue protocol. The replaceable adapter leaves that work separate.

Browser validators are compiled from the same authored schemas before launch; CSP permits neither runtime evaluation nor external scripts. Message text is rendered with `textContent`. The runtime checks exact Host and, when present, Origin; accepts JSON mutations only; bounds bodies to 128 KiB and uses a shared 60-token bucket refilling one token per second. The database listens only on loopback, requires its private SCRAM password and runs product queries as non-owner `agora_app`. Migration credentials never serve product queries.

### Selected messages to a cited proposal

```flow
Selected messages | A trusted caller supplies validated persisted records and an explicit list of stored message IDs from one project and room; no storage handle enters the core.
Bounded context | Refuse more than 100 supplied records, more than 10 selected IDs, or more than 4096 selected body scalars. Sort numerically by room sequence, never timestamp; freeze a private copy and digest it.
Deterministic proposal | Emit exact quotes with the not-AI label. Bind the requester, project, room, request ID and selected content to deterministic identities, with no provider or execution authority.
Cited records | Every claim names its selected stored message ID and exact sequence. Unknown, foreign or unselected citations deny; there is no transitive citation lookup or generated URL.
Posting boundary | The SQL adapter calls the pure core after loading selected rows under the room lock, then checks the output message bound and writes a local-agent message, event and receipt atomically. The pure core still has no effect handle.
```

The [context compiler](repo:packages/domain/src/local-answer/context.ts), [citation constructor](repo:packages/domain/src/local-answer/citations.ts), [proposal function](repo:packages/domain/src/local-answer/proposal.ts) and [future posting port](repo:packages/domain/src/local-answer/posting.ts) are separate files. The adapter adds the closed [LocalAnswerCommand](repo:contracts/schemas/local-room.schema.json) wire shape; the pure core still uses domain values and has no posting authority. **In progress: L1-L3 landed, L4 first slice landed, L5 selected-quote posting slice implemented; remaining L4 and L5 scope open.** Snapshot history is bounded to the latest 1000 messages. Older immutable records remain readable through event replay in pages of 50; this disposable runtime has no event compaction or retention expiry. CLI replay prints one page; continue with the last event's `seq`. The client drains at most 200 pages per call, then reports the bound and can resume again.

There is no login, production membership, search, upload, external provider, model-generated agent response, task, repository authority, publication, cloud execution or implementation of the approved visual baseline. Reset creates a new disposable database, not a historical continuation, so reload the room page after reset. A crashed supervisor with ambiguous surviving resources is refused rather than adopted or killed by a stored PID. See [operator recovery](operations.md#local-room-lifecycle). These receipts do not qualify FG04-FG08, AC02, AC04 or the S1 release.

**L5 end-to-end response slices:** A selected message can be quoted by browser or CLI, with a persisted, labelled local-agent record and direct citations. The browser now retains a pending action ID across failed delivery/reload and clears it after receipt, allowing intentional later quotes. Tests cover this retry lifecycle and resolve the stored citation to the exact source ID, sequence and body. Still not qualified: coordination of independently triggered actions across tabs, browser reload and distinct-tab end-to-end response drive for this follow-up, broader L5 user acceptance, independent review and hosted qualification. There is no conversational creation or natural-language Ask center prompt, provider inference or broader retrieval.
